## 2. Анализ perf report для связного списка

Сценарий 1 (50 000 find):

|          Функция         | % времени |
|--------------------------|-----------|
|       __strcmp_avx2      |   73.83%  |
|         listFind         |   22.43%  |
| strcmp@plt (вызов strcmp)|   2.80%   |

Почти всё время (~99%) потребляет путь поиска. Основное время тратится в функции strcmp, что ожидаемо при линейном поиске в списке. Для каждого запроса find приходится в среднем обходить 4550 элементов (половину от 9100), выполняя сравнение на каждом шаге.
Доля listFind (~22%) — обход указателей: узлы выделены в куче в разное время, каждый переход по указателю может потенциально дать промах кэша.

Сценарий 2 (10 000 insert + 10 000 find):

|            Функция           | % времени |
|------------------------------|-----------|
|         __strcmp_avx2        |   52.17%  |
|           listFind           |   17.39%  |
|   strcmp@plt (вызов strcmp)  |   13.04%  |
| irqentry_exit (прерывани ОС) |    ~13%   |

Картина та же, strcmp ~65% суммарно, при этом listInsert в топе отсутствует — вставка в голову списка O(1). Строка irqentry_exit — шум ОС: запуск
короткий, и таймерные прерывания дают заметный процент.

## 3. Объяснение разницы

### Асимптотика операций

| Операция | АВЛ-дерево | Односвязный список |
|----------|------------|--------------------|
|   find   |  O(log n)  |        O(n)        |
|  insert  |  O(log n)  |    O(1) в начало   |
|  delete  |  O(log n)  |        O(n)        |

### Почему АВЛ-дерево быстрее на find

Для базы из 9100 записей:
- АВЛ-дерево выполняет ~13 сравнений (log₂ 9100)
- Список выполняет ~4550 сравнений в среднем

Разница в 350 раз на одну операцию. При 50 000 запросов это даёт ускорение в десятки раз.

### Меняется ли соотношение для insert

Для insert список может быть быстрее, если вставлять в начало (O(1) против O(log n)). Однако во втором сценарии операции find чередуются с insert, и линейный поиск занимает больше времени, поэтому АВЛ-дерево всё равно выигрывает.

## 4. Вывод

Переход на АВЛ-дерево обеспечивает ускорение операций поиска в примерно 50 раз на текущем датасете из 9100 аэропортов. Это устраняет задержки на стойках регистрации и позволяет системе масштабироваться при росте базы данных. Рекомендуется использовать АВЛ-дерево вместо списка.
